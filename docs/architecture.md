# Architecture

## Implemented scaffold

`infra/docker-compose.yml` builds `docker-image-creator-web:local` from `apps/web/Dockerfile`, `docker-image-creator-api:local` from `apps/api/Dockerfile`, and `docker-image-creator-runner:local` from `apps/runner/Dockerfile`, and runs `mysql:8.4.11`. All four join the Compose project-scoped `infrastructure` bridge network. MySQL stores data in the project-scoped `mysql-data` named volume. API, MySQL, and runner publish no host ports. Web publishes port 8080 on loopback by default.

Deployment configuration comes from the repository root `.env`, explicitly selected by the human operator with `docker compose --env-file .env -f infra/docker-compose.yml`. Only declared MySQL variables are passed into MySQL. API configuration now includes `DATABASE_URL`, `AUTH_ACCESS_TOKEN_SECRET`, and `AUTH_TRUSTED_ORIGINS`. Use the root `.env.example` as the secret-free configuration template. API code, Prisma configuration, and agent checks do not load environment files; source development uses exported process variables.

The Vue 3/Vite application uses strict TypeScript and `<script setup lang="ts">`. Its built assets are served by Nginx, which proxies `/api/` to `api:3000`. Nest exposes liveness and the [authentication endpoints](authentication.md), with shared transport interfaces in `packages/contracts`. Liveness itself does not query the database, but API startup now requires a database connection. Compose waits for an authenticated MySQL `SELECT 1` before starting API, then for API health before starting web, using [Compose health dependencies](https://docs.docker.com/compose/how-tos/startup-order/). The API container applies committed Prisma migrations before starting Nest.

Build stages use `node:22.23.4-bookworm-slim` and pnpm 10.34.9. The frontend runtime uses `nginx:1.28.0-alpine`; the API runtime runs as the `node` user. Only the private runner mounts the Docker socket. Build contexts allowlist source/config inputs and exclude environment files, dependencies, and runtime artifacts.

The API image additionally includes OpenSSL for Prisma migration tooling, the schema/migrations, and its Prisma configuration. Prisma CLI remains in the image for startup migrations. Build-time client generation uses a placeholder URL and never requires production credentials. The generated CommonJS client is compiled into the API output and is not tracked in Git.

The pnpm workspace uses pinned direct package versions and a resolved `pnpm-lock.yaml`. Both Dockerfiles install with `--frozen-lockfile`. Container boot remains a separate verification gate. See [local setup](local-setup.md).

### Docker development

The optional `infra/docker-compose.dev.yml` override runs API and web from the shared `infra/Dockerfile.dev` image as the unprivileged `node` user. Dependency manifests are copied before source to cache installation. Mounts expose only application source, shared contracts, and selected non-secret configuration. Frontend/contracts/config mounts are read-only; API source is writable so Docker can create the empty generated-directory mountpoint on a clean checkout. Generated Prisma files use an anonymous Docker volume over that subtree. Host dependencies and private environment files are never mounted. Docker's init process forwards signals and reaps child processes.

Vite listens on internal port 5173 and replaces Nginx in this mode, preserving the configured loopback `WEB_PORT` through a [Compose port override](https://docs.docker.com/reference/compose-file/merge/#replace-value) (Compose >= 2.24.4). Its server-side proxy uses `API_PROXY_TARGET=http://api:3000`; browser requests and API origin checks remain unchanged. Local Vite defaults to `http://127.0.0.1:3000`. Vite still disables environment-file loading. `DEV_WATCH_POLLING=true` enables polling in both watchers for hosts without reliable mount events.

API development uses TypeScript's watch compiler and the existing strict/decorator-metadata settings. After each successful complete compilation, a small process supervisor terminates the previous Nest process, waits for shutdown (forcing it after five seconds), and starts the new compiled entry point. Invalid edits leave the last valid server running. SIGINT/SIGTERM close the watcher and child server. Startup deploys committed Prisma migrations and regenerates the client; schema/migration changes require an API restart. Dependency changes require rebuilding the development image; environment changes require recreating containers. The original single-file production deployment remains available, and both modes retain the same project-scoped database volume. See [local setup](local-setup.md) for switching commands and the disposable live-reload check.

## Implemented configuration generation (2026-10-30)

[ADR 0002](adr/0002-compose-only-generation.md) supersedes custom builds with approved public images and fixed Node/Python HTTP starters. [Configuration API](configuration-api.md) documents implemented creation, shared contracts, DTO/catalog validation, immutable initial revisions, and encrypted generation inputs/output/secrets. Only one Compose document is generated, without Dockerfiles or adjacent authored source files. A deterministic fake sits behind the provider adapter; live provider selection remains deferred.

`POST /configs` saves a configuration and queued job transactionally and returns 202. An API lifecycle worker claims MySQL jobs with `FOR UPDATE SKIP LOCKED`, server-generated fencing tokens, and two durable global slots. User-row locking admits at most one outstanding job per user. Generation has a five-minute deadline, 30-second lease grace, and 15-minute queue bound. Queued jobs survive restart; expired running jobs fail without automatic provider replay. Worker shutdown aborts active generation and finishes bookkeeping before Prisma pools disconnect.

The compiler emits JSON-formatted YAML with fixed images/commands, project labels, a project-scoped bridge network, resource/log limits, optional loopback ports, and named database volumes. Returned output is retained encrypted before validation; only safe server-compiled content is written. A flushed temporary file is renamed to `.runtime/configs/<user>/<config>/<revision>/compose.yaml` before success and the immutable revision commit together. Files are mode 0600, directories 0700, and paths reject symlinks. Failed uncommitted artifacts are removed or tracked for retryable cleanup. Source defaults to the ignored repository tree; Docker uses a persistent `generated-configs` named volume at `/app/.runtime/configs`.

Vue creation/list/detail pages poll with short authenticated HTTP requests and no overall browser deadline. Temporary transport errors back off without another creation request; re-opening a saved configuration resumes polling. Owner-scoped UUID idempotency keys make lost creation responses retryable. Tokens continue using the existing memory-only session/serialized refresh flow.

Configuration deletion (2026-11-01) is an owner-scoped API operation that retains database history and encrypted secrets while marking the configuration deleted. Normal reads hide it, its quota slot is released, and reuse of its original creation key returns 400. Queued/running generation prevents deletion with 403; a successful DELETE returns 204 and repeated deletion returns 404. A durable configuration cleanup marker is committed with deletion before removing its private artifact directory. The API attempts removal immediately; the lifecycle worker retries failures after restart in bounded batches. Cleanup does not create missing directories or follow symlink roots/parents. File publication now takes the same configuration-row lock as deletion and validates deletion state and lease before writing, preventing late publication after deletion. No runner or Docker-resource cleanup is introduced; restoration and eventual database purging remain outside this slice. Vue list and detail pages share a confirmed deletion control through the authenticated config client. It disables deletion during generation or a pending request, handles 404 as already removed, and exposes retryable errors. Deletion removes the list row or returns detail to the list; a list refresh updates generation status without restoring locally deleted rows.

The API never accesses Docker. A current `succeeded` job means generation and file/DB persistence succeeded, explicitly accompanied by `provider: fake` and `runtimeValidation: not_performed`. Only the future private runner may pull/start containers, check readiness, observe for ten seconds, stop trials, reconcile Docker resources, or manage lasting deployments. Database readiness probes, actual image startup verification, and secret injection remain runner prerequisites.

## Implemented execution endpoint slice (2026-11-02)

The [runtime API](runtime-api.md) implements owner-scoped Start/Stop, durable operation polling, and deployment state. Start requires an explicit saved revision and UUID idempotency key. User-row locking and unique reservations enforce one running configuration per user with no global running count quota; starting, stopping, partial, and unknown state retain the slot until all services are verified stopped. Ports are reserved transactionally. Failed Start rolls back its own services without deleting data. Runtime-backed configurations use asynchronous DELETE through the same runner queue, after services are verified stopped.

The separate Nest runner claims MySQL operations, validates saved specs again, compiles a stricter isolated runtime manifest, privately supplies encrypted secrets, pulls images, waits for authenticated readiness, and reconciles scoped Docker state without automatically restarting workloads. Its bootstrap shares the API build's compiler/Prisma code but is not imported by `AppModule`; `apps/runner` provides its package command and dedicated image. The default Compose file gives only this service the local daemon socket and starts it after API health/migrations. The console milestone adds ticket-authenticated private WebSocket transport on internal port 3001 without publishing a host port.

The default-runner follow-up moves the runner service from a separate opt-in overlay into `infra/docker-compose.yml`, removing the overlay. Ordinary production and development startup now include the queue consumer, so Start/Stop no longer require an extra Compose file. The development override still changes only web/API; runner uses its compiled image and must be rebuilt after runtime source changes. The live-reload smoke harness explicitly starts web/API/MySQL, keeping runtime execution in its separately verified smoke gate. Docker Engine 28+ remains required; moving the service does not change execution policy or upgrade the host.

Engine 28+ and working resource enforcement are execution prerequisites. The earlier Engine 27.1.2 prerequisite failure is historical; the host now reports 28.1.1. Inspect validation accepts either `NET_RAW` or Docker's canonical `CAP_NET_RAW` for the required dropped capability. A read-only live comparison verified this fix against healthy containers previously rejected with `RESOURCE_CONFLICT`; the deployed runner still requires rebuilding. API/controlled-driver integration and runner image verification are distinct from successful supported-host Docker smoke checks; the latter remain pending. The initial endpoint slice did not complete milestone 5 or add automatic trials, runtime cleanup, or terminals; the deletion follow-up below adds stopped-resource cleanup.

The configuration-detail UI follow-up adds a runtime client using the existing shared transport contracts and a Vue composable for deployment/operation polling, cancellation, and explicit Start/Stop submission. One action appears to the left of Delete, with disabled Starting/Stopping states, and a lifecycle label replaces the Generation line. Runtime status is fetched on page load and after explicit actions; polling follows pending operations or starting/stopping deployments, then stops when settled. Unconfirmed action responses and transient status failures keep recovery checks active with backoff and a manual retry. External changes after polling stops require a page reload or explicit action. Operation errors remain separate from observed deployment state. Lost action responses retain their idempotency key for an explicit retry, while confirmed terminal attempts get new keys. The detail page allows deletion after runtime absence or stopped state is known and blocks it while runtime status/actions are unresolved; deletion in flight blocks Start/Stop. The API remains authoritative for ownership, concurrent operations, admission, and deletion policy.

### Per-service observation view (2026-11-03)

The implemented [container view](runtime-api.md#per-service-container-view) extends configuration detail with read-only per-service runtime observations. The runner remains the only Docker observer; the API serves owner/configuration/applied-revision-scoped safe summaries through shared transport contracts and `GET /configs/:id/services`. Migration `20261103000000_service_observations` adds a nullable JSON snapshot to Deployment, written in the same fenced transaction as aggregate observations. This slice needs current summaries rather than an independently managed service-instance lifecycle; the previously planned ServiceInstance/terminal identifiers remain future work. A revision change clears the previous snapshot. The API explicitly selects and validates safe fields against the deployment's applied revision instead of returning stored JSON wholesale.

Raw inspect output, container IDs, and environment values remain private. Container state, health, observation availability, and verified absence remain distinguishable; aggregate deployment state cannot substitute for per-service evidence. Independently trustworthy observations remain available when another service cannot be inspected. Listing/network failures clear the snapshot; an unknown running state never releases a reservation. Start/Stop retain their existing strict ownership/policy checks.

The browser loads the latest available observations with configuration status on page entry and through the existing Start/Stop operation flow, including failures, then stops fetching once status settles. Runner reconciliation continues independently. API failures retain visibly stale observations or show Unknown when no previous observation exists; verified absence is required for Not created. This view adds no terminal transport, logs, metrics, per-container actions, or ongoing idle polling.

### Container terminals (2026-11-03)

The implemented [terminal API](terminal-api.md) adds per-running-service Connect and `/configs/:id/console/:service`. The same-tab xterm.js page returns to configuration detail on shell exit, Disconnect, or connection/authorization failure; it never reconnects automatically or stops the main container. Authentication-ended navigation shows only a sign-in notice without private API reads.

`TerminalModule` owns authenticated HTTP ticket issuance and the public WebSocket relay. Migration `20261103010000_terminal_tickets` stores only hashes of 30-second one-use tickets bound to user, auth session, configuration, applied revision, deployment operation, and service. The browser sends its ticket in the first WebSocket message after an exact Origin check; the API forwards it privately in an Authorization header. `TerminalRunner` atomically consumes it, revalidates saved manifests/digests and live resource policy/labels, and opens a TTY through a small Node HTTP Engine API v1.48 client. Only the runner registers the Engine provider or mounts the Docker socket. Nginx and Vite proxy WebSocket upgrades; ping/pong keeps healthy idle transports open.

Bash falls back to sh. Exec inherits container user/working directory and grants no additional privileges; there is no command allowlist within those permissions. Runner checks active authorization and container state every second. Disconnect verifies resource ownership/policy before terminating the exec shell and foreground group; deliberately detached jobs may survive. Graceful shutdown waits for setup/cleanup before disconnecting Prisma. Daemon outages, forced runner termination, or user removal of cleanup tools can prevent cleanup; Stop remains recovery. There is no host shell behind the terminal, and browser closure cannot guarantee detection/containment of a real container escape.

The user explicitly rejected terminal idle timeouts, maximum session lifetimes, and connection-count quotas, superseding those planned defaults. Authentication-session expiry and existing container resource limits remain. Transport frame/pending-buffer bounds, limited browser scrollback, fixed resize bounds, protocol liveness and establishment deadlines protect memory and detect broken connections without imposing healthy-session timeouts. Terminal content is not recorded; clipboard/window escape integrations are disabled. The private runner transport stays on the trusted infrastructure network with no TLS or public ingress. See [terminal setup and verification](terminal-api.md).

## Target stack

The [2026-11-01 decision](adr/0003-shared-host-execution.md) retains a private runner and user containers alongside application containers on the same host. The endpoint/runner slice above implements this arrangement subject to the supported-host verification gate; later runtime workflows remain planned.

- Backend: NestJS with strict TypeScript, validation, REST endpoints, and an authenticated terminal gateway.
- Frontend: Vue 3, Vite, Vue Router, Pinia for session/application state, and xterm.js for terminal display.
- Persistence: MySQL with Prisma migrations; MySQL-backed sessions and durable operation records avoid requiring Redis for the MVP.
- Agent: provider-neutral adapter producing structured validated output through a bounded generation loop.
- Execution: separate NestJS runner process using Docker Compose v2 for lifecycle operations and Node HTTP over the local Engine socket for create/start/resize/inspect exec calls.
- Workspace: pnpm; initial versions are pinned in manifests and Dockerfiles, with clean installation and full compatibility checks still pending.

## Repository layout

```text
apps/
  api/                 # auth, catalog, configs, generation, operations, terminal gateway
  web/                 # Vue pages, UI components, API client, terminal adapter
  runner/              # private runner package/image; default Compose service
packages/
  contracts/           # versioned schemas, API types, operation/terminal events
infra/                 # application Compose files and development infrastructure
docs/                  # planning and subsequent operational documentation
```

`apps/api`, `apps/web`, `apps/runner`, `packages/contracts`, and `infra` exist. The default Compose stack includes web, API, MySQL, and runner. The execution worker remains a separate process; the API process never registers it.

## Request and execution flow

The browser talks only to the API. The API validates requests, checks ownership, persists revisions and operations, and makes bounded generation calls. A separate runner claims durable operations from MySQL using atomic leases and executes them against its Docker daemon. The API relays terminal traffic over an authenticated private runner connection; the browser cannot reach the runner directly.

The runner receives internal IDs, then loads validated revision data. It must not accept arbitrary Compose paths, host paths, commands, or Docker container IDs from a browser. Its internal terminal protocol authenticates the API and binds each session to an owned stack, service, and deployment. Worker credentials, database permissions, and network placement must be documented when provisioning it.

## Infrastructure separation

The application's API, database, and private runner transport use an infrastructure network. Generated services join only their own configuration's project-scoped bridge network. The agreed execution policy denies workload access to other configurations, application infrastructure, and the internet; services within a configuration may communicate. Terminal access uses Docker exec and requires no published service ports. The existing compiler still emits ordinary bridges and optional loopback ports: adapting saved configurations to the execution policy and verifying host/gateway denial remain execution prerequisites. Only the private runner may access the host Docker daemon; daemon access remains privileged even inside a container.

## State and durability

A saved configuration has immutable revisions; generation attempts and runtime operations are separate records. A deployment points to its applied revision. Store desired state separately from observed Docker state. Poll and reconcile server-owned labels after restarts, runner lease expiry, crashes, and out-of-band Docker changes. Do not infer successful execution solely from a database flag or a lost HTTP response.

Only one mutating operation per stack may execute at a time. Leases, operation attempt IDs, idempotency keys, and reconciliation prevent duplicate effects. A timed-out worker may have left running containers: fence its attempt and inspect Docker before retrying. Retain volumes on failures and surface partial results.

## Decisions and open choices

The separate runner, durable MySQL operations, immutable revisions, and structured generation contract are planned defaults. Resolve LLM provider/model, specific image tags, terminal/Engine client libraries, resource caps, and secret-key provisioning during their implementation milestone. Public hosting requires a separate execution isolation design.

### Execution design discussion (2026-11-01)

The user chose generated containers alongside the application containers, with one private network per configuration, superseding the earlier literal-nesting request. [ADR 0003](adr/0003-shared-host-execution.md) records the shared-host/private-runner decision. Docker access stays exclusive to the runner; the API authenticates requests and relays authorized traffic. Network isolation must be tested separately from Docker ownership checks.

Generated services may communicate within their configuration but must not reach the internet, other configurations, or application infrastructure. The runner may fetch approved images separately from workload networking. Honor explicitly requested loopback port mappings after checking conflicts; terminal access adds no published ports. No nested daemon or per-user VM is planned for this slice. The agreed audience is trusted accounts on a dedicated local Docker host. Public, mutually untrusted hosting would require a separate isolation design and is outside this milestone.

The connection experience is implemented as a per-service Connect button opening a container shell. For generated MySQL, users can use the image's `mysql` CLI and inherited container environment; the application does not inject passwords into terminal commands or record terminal content. Actual SSH and a browser database GUI are not required. Multiple independently authorized terminals can connect simultaneously, including to the same container. No terminal idle/lifetime/count limits or automatic reconnection are introduced; see the console milestone above.

Start on an existing saved configuration launches a lasting deployment; it does not stop automatically after a trial. Explicit Stop preserves database data for the next Start. A failed Start stops services launched by that attempt, preserves volumes/files, and retains bounded diagnostics with cleanup failures reported separately. API/runner restarts leave running workloads alone. Unexpected service exits or a host reboot require an explicit Start; reconciliation reports actual state rather than automatically relaunching services.

Allow one running configuration per user, with no global running-configuration count limit. Existing per-service CPU/memory/PID/log limits remain; this does not remove bounded worker concurrency or deadlines. Concurrent admissions must not start two configurations. Starting, stopping, partial running state, and unknown state retain the reservation until all services are verified stopped.

The deletion follow-up implements DELETE admission and a durable `delete` runtime action for stopped deployments. The API serializes deletion with Start/Stop under owner/configuration locks, records deletion intent, and returns 202. The runner checks stopped state and ownership/policy again, removes containers without force or volume flags and removes the isolated network, verifies absence, and removes artifact files before a fenced transaction hides the config/releases saved-config quota. Runner and API share `generated-configs` and `CONFIG_ARTIFACT_ROOT`; only the runner has the Docker socket. Failed/expired deletion remains visible and retryable, and deletion intent blocks subsequent Start even after partial cleanup. Stop remains available after a terminal cleanup failure for recovery from externally restarted containers. Reconciliation cannot mistake stopped containers for completed deletion. Matching-key replay and owned delete-operation status remain available after success, preventing a lost final HTTP poll. Never-started configs retain their immediate 204 deletion path. Volumes and their recovery metadata/secrets/history are retained; the separate confirmed persistent-data deletion action remains future work.

Execution with deterministic generation precedes console, then real LLM integration. Automatic temporary validation remains a separate later slice. The endpoint slice recompiles older saved specs into runtime manifests without changing immutable revisions. Configuration-detail runtime UI is implemented; full supported-host verification and explicit persistent-data deletion remain unfinished; see the [implementation plan](implementation-plan.md).

### Auth decision: access and refresh tokens (2026-10-30)

The requested API uses bearer access JWTs plus opaque refresh tokens instead of the original cookie-session plan. Access tokens last 15 minutes; sessions have an absolute seven-day lifetime. MySQL session checks make logout/replay revocation immediate. Refresh-token consumption and replacement occur in one transaction; replay revocation commits before returning 401. Simultaneous refresh requests intentionally revoke the session, so clients must serialize refreshes.

Prisma 7.10.0 uses the maintained MySQL/MariaDB driver adapter and the [`prisma-client` generator's CommonJS support](https://www.prisma.io/docs/orm/v7/prisma-schema/overview/generators). Unlike the legacy generator, it does not load environment files at runtime. Prisma configuration likewise has no dotenv import. Connection pools are bounded to five with five-second connection/acquisition timeouts; timestamps use UTC. Database URL components must be URL-encoded; URL query options/fragments are rejected rather than silently ignored. The current adapter setup targets the private local MySQL network; remote TLS configuration is not implemented. It explicitly permits [server RSA-key retrieval](https://mariadb.com/docs/connectors/mariadb-connector-nodejs/node-js-connection-options) for MySQL 8 caching_sha2_password on that network and disables query-parameter logging.

`AuthModule` owns controllers, credential validation, tokens, origin/rate controls, and Prisma persistence. `AccessTokenGuard` is exported for protected modules; new protected controllers must use it explicitly. The health route is public. Shared request/response interfaces live in `packages/contracts`; no ORM model crosses that boundary. Backend tests use actual Nest HTTP handling and disposable MySQL, with no mocked persistence or paid services. Terminal authorization uses the same MySQL sessions; cookie transport/CSRF mechanisms, expired-session cleanup, and auth-session quotas remain planned.

### Browser authentication (2026-10-30)

Vue Router exposes `/login`, `/register`, and the protected `/account` landing page. Root and unknown URLs resolve to the account page for signed-in users and login for guests. Configuration creation/list/detail routes are implemented with background status polling; the detail page also provides Start/Stop and a runtime status label. Pinia exposes the current user and authentication actions; tokens stay in a private session-client closure, outside Pinia's serializable state and browser storage. Reloading or closing a page requires a new login. Reloading does not revoke the server session; explicit logout calls the API to revoke it.

The client uses same-origin `/api/v1/auth` requests with cookies omitted, no-store caching, and ten-second request deadlines. It checks `/me` on account entry, refreshes before requests within five seconds of access expiry or after a 401, shares one in-flight refresh, and retries a protected request at most once. A delayed 401 for an old access token reuses the already-rotated token. Failed or lost refresh responses clear local credentials rather than replaying a potentially consumed refresh token. Generation checks prevent late responses from restoring a logged-out session. Retryable logout failures keep the logout control available until revocation can be confirmed. Ordinary pages detect revocation on API use; active terminals additionally check the underlying session every second in the runner.

Vitest and Vue Test Utils exercise the real Vue views, router, Pinia store, and session client with mocked HTTP responses; these tests do not replace the disposable-MySQL backend suite. Vite and Vitest both disable environment-file loading.
