# Generate Compose and Dockerfile bundles and validate them by running

The Dockerfile/build portion and generation deadline of this decision are superseded by [ADR 0002](0002-compose-only-generation.md). The historical choices below explain the earlier design; the temporary Docker validation lifecycle remains planned, not implemented by configuration creation.

On 2026-10-30, the user expanded generation from Compose settings for existing images to a complete bundle containing Compose files and Dockerfiles, ready to build and run without manual file completion. Every returned LLM response is saved in the database before attempting execution, including responses that subsequently fail validation. Generation includes an automatic validation run: successful services are stopped and the action is recorded as successful; on failure the action is recorded as failed, generated files are removed from the file tree, and the returned configuration remains in the database.

This replaces the earlier scope that deferred Dockerfile generation and prohibited all automatic execution after generation. A validation run is temporary; a user explicitly starts a lasting deployment after review. Saving returned content does not authorize executing it: policy checks still precede builds and startup, only the runner accesses Docker, and ownership and resource isolation still apply.

The user subsequently accepted complete generated build inputs within a restricted bundle format and approved base-image catalog; the initial supported workloads remain Node.js, Python, MySQL, and MongoDB. Every service must pass a service-specific readiness check and remain running for a ten-second observation period. Successful attempts retain their files and stopped containers; failed attempts remove their containers and networks before deleting generated files. Named volumes are preserved until an explicit data-deletion action, and cleanup failures are tracked separately.

The generation endpoint returns 202 with an action ID for polling, and the first version makes one generation attempt without automatic LLM repair. MySQL is authoritative for specifications and metadata; files under the ignored `/.runtime/` directory use server-generated configuration/revision paths and recorded digests. Provider integration starts with an adapter and deterministic fake; a real provider and model are still unselected, and no credentials or paid calls are authorized by this decision.

The final interview round accepted minimal starter applications, catalog-approved Dockerfile forms with declared Node/Python dependencies, the explicit deadlines and quotas in the [generation design](../generation-and-runtime.md), encrypted original responses with masked previews, and passwords generated outside the model. Oversized responses fail with explicitly marked bounded/truncated capture. Validation retries use fresh attempt-owned resources; infrastructure failures leave bundles unverified, and explicit revalidation can reuse stored content without another model call. Incomplete cleanup records `cleanup_pending` and retains necessary recovery files; only exclusively owned failed-attempt images may be removed, and volumes require explicit deletion. None of this generation behavior is implemented yet.
