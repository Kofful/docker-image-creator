# MySQL credentials containing special characters

The C09 reproduction with `mysql:8.4.11` failed with SQL error 1064 during application-user creation. The stock image's initializer places passwords directly inside SQL string literals. YAML quoting and shell quoting do not fix this SQL boundary. Do not pre-escape stored credentials or their environment values.

Prompt version 4 includes `mysqlBootstrap` reference data only when MySQL is requested. `apps/api/src/configs/mysql-bootstrap.example.ts` contains the command and health-check arrays. The model is instructed to copy these arrays into its Compose document, using block scalars or YAML string quoting. Dollars are already escaped for Compose and must not be escaped again. This remains direct model-authored Compose: no postprocessing, runtime injection, extra mount, image build, provider call or repair is introduced. Model compliance is still required; routine regression tests do not establish a live model pass rate.

The command uses Bash, gosu, MySQL clients and the entrypoint functions shipped in the pinned image. It prepares the image-owned directories before dropping privileges, then installs initialization overrides as the mysql user so the stock privilege-change re-exec cannot discard them. The image's existing-data check skips initialization on subsequent starts. Root and application passwords remain unchanged in the environment; only temporary SQL literals are encoded. Single quotes are doubled under session `NO_BACKSLASH_ESCAPES`; the binary-mode, UTF-8 SQL client preserves backslashes and line endings. Database identifiers are quoted separately. Client authentication uses environment values rather than embedding credentials in command arguments or option files. SQL-client stderr is suppressed to avoid printing a failing statement containing a credential; failures emit fixed messages.

The bootstrap creates the requested database, application account/grant, local root account password and the image's configured remote root account. It retains stock timezone-table initialization and uses the stock temporary server and final mysqld lifecycle. The example is tied to the pinned entrypoint implementation and must be retested when the MySQL image changes.

Readiness executes an authenticated application-user `SELECT 1` over loopback TCP against the requested database, with the normal policy timing. `mysqladmin ping` alone does not prove authentication.

## Verification and use

`pnpm test:compose-validation` verifies that the exact prompt example fits the strict policy and survives saved-revision validation without rewriting. `pnpm test:compose-provider` exercises the shared prompt with mocked HTTP and retains secret exclusion and unchanged model output checks.

`pnpm test:evaluation:runtime` includes a C09 regression that obtains the example from the actual prompt, serializes it into a test-only policy fixture, and launches it through the existing runner driver. It checks exact environment delivery, application/root authentication, incorrect-password rejection, marker insertion and retention across Stop/Start of the same artifact and named volume. The test creates random ownership-scoped resources and verifies cleanup; it does not use the application database, protected environment files or live inference. The original stock-command version of this test reproduced `START_FAILED` before the reference was applied.

Verification: both new Docker regressions passed against `mysql:8.4.11`: the unchanged C09 suite values, and an extended case with quotes, backslashes, dollars, Unicode, SQL-like text, CRLF and trailing newlines in both root and application credentials, plus an underscore-containing database name. Both verified authentication, denial of wrong passwords and persistence over Stop/Start. All 41 provider checks, 89 policy checks, evaluator/driver suites, API TypeScript checking and changed-source lint passed. No live inference, deployment or full four-image runtime rerun was performed for this follow-up.

Rebuild and recreate API/runner through the normal operator workflow before using the new prompt in deployed generation or evaluation. Development API reload alone does not update the runner's compiled evaluator. New evaluations should report prompt version 4. Previously generated artifacts, including the failing C09 artifact, are not repaired; generate a new revision. Existing production volumes are never reinitialized by this change, and it does not recover an already half-initialized failed volume.
